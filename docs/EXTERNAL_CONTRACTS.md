# External Contracts — enji-auth Issuer & Collector Integration

**Purpose**: This document defines the boundary between this library (token verification) and external systems (token issuance, employee identity resolution).

**Audience**: Maintainers, AI agents, security audits.

## Issuer: enji-auth Service

**Role**: Creates (mints) JWT tokens with encrypted sensitive claims.

### Location

- **Encrypt/decrypt**: `be/services/enji-auth/app/auth/authentication/cipher.py`
  - `encrypt_payload(data: dict, secret: str) → str` — encrypts sensitive claims
  - Public implementation mirrors this library's `decrypt_payload`
  
- **Token mint**: `be/services/enji-auth/app/auth/authentication/core.py`
  - `_create_jwt_token(**kwargs) → str` — creates JWT with plaintext + encrypted payload
  - `_PLAINTEXT_CLAIMS = frozenset({"exp", "type"})` — only these go outside `enc`
  
- **Employee ID lookup**: `be/services/enji-auth/app/auth/authentication/helpers/collector_client.py`
  - `get_employee_id_by_email(email: str) → int` — fetches from Collector API
  - `ensure_employee_id_by_email(email: str) → int` — fetches or provisions on-demand

### Identity Sources

| Claim | Source | Meaning |
|-------|--------|---------|
| `sub` | enji-auth auth source (OIDC, LDAP, local) | User email address |
| `user_id` | enji-auth database | Unique user ID within enji-auth |
| `employee_id` | **Collector API** (`/employees/get_id_by_email`) | Employee ID from Collector database; provisioned if missing |
| `roles` | enji-auth database + role hierarchy | User roles (e.g., `["admin", "editor"]`) |
| `permissions` | enji-auth database | User permissions (exact match or regex patterns) |
| `disallows` | enji-auth database | Explicitly blocked permissions (override `permissions`) |

## Shared Crypto Contract

### HKDF Key Derivation

**Info string** (compatibility domain):
```python
info = b"enji-jwt-payload-encryption"
```

This string **must** be identical in both issuer and verifier. It ties the encryption key derivation to this specific JWT format — if changed, all tokens become undecryptable.

**Key derivation**:
- **Algorithm**: HKDF-SHA256
- **Length**: 32 bytes (AES-256)
- **Salt**: `None` (implicit `b""`)
- **Secret**: Service shared secret (same across issuer and this library's verifier)

### AES-GCM Encryption

- **Cipher**: AES-256-GCM
- **Nonce**: 12 random bytes (generated by issuer, prepended to ciphertext)
- **Nonce size**: Locked at 12 bytes; hardcoded in both issuer and verifier
- **Tag size**: 16 bytes (implicit, built into GCM)
- **AAD**: `None` (no additional authenticated data)

### Payload Compression

- **Method**: zlib (`level=Z_BEST_COMPRESSION`)
- **Ratio**: ~70–80% reduction for typical (roles + permissions) payloads
- **Rationale**: Compact final token size (double base64 expansion in JWT format)

### Wire Format (Base64url)

```
wire_token = base64url(nonce || ciphertext_with_tag)
           = base64url(12_bytes_nonce + N_bytes_encrypted_payload)
```

The JWT `enc` claim contains this base64url-encoded blob, making it safe to embed in JSON.

## Claim Placement: Plaintext vs. Encrypted

### PLAINTEXT Claims (visible in JWT without decryption)

```json
{
  "exp": 1706569200,    // Unix timestamp
  "type": "access"      // Token type
}
```

These are **not** inside `enc`. Any platform or middleware decoding the JWT can see them without the secret.

**Contract**: enji-auth **must** always include `exp` and `type` as plaintext claims.

### ENCRYPTED Claims (inside `enc` blob)

After decryption and decompression, these claims appear in `JWTClaims`:

```json
{
  "sub": "user@example.com",      // Email (from public claim in raw JWT, but sensitive)
  "user_id": 123,                 // Unique user ID (from enji-auth)
  "rand_str": "uuid-randomstring", // Nonce for token uniqueness
  "roles": ["admin", "editor"],   // User roles
  "permissions": ["read", "write"], // Permission patterns
  "disallows": [],                // Blocked permissions
  "employee_id": 321              // From Collector database
}
```

**Contract**: enji-auth **must** encrypt all identity, role, and permission data inside `enc`.

### Rationale for Separation

1. **JWT inspection**: Platforms can validate expiry without decryption.
2. **Forward compatibility**: New encrypted claims don't change the JWT header/public payload shape.
3. **Selective encryption**: Public/sensitive claims could use different protection (not currently).

## Employee ID: Collector Database Integration

### What is `employee_id`?

- **NOT** the same as `user_id` (which is from enji-auth).
- **IS** the employee record ID in the **Collector database**.
- Fetched by enji-auth **at token issuance time** via Collector API.
- Embedded in the encrypted `enc` payload.

### Why Separate Systems?

- **Collector**: Central employee database (HR source of truth, historical records, permissions per department).
- **enji-auth**: Authentication service (user credentials, role hierarchies, external IdP integration).
- **Token**: Carries both `user_id` (auth) and `employee_id` (HR identity) for services that need HR context.

### Lookup Flow at Issuance

1. User authenticates to enji-auth (LDAP, OIDC, or local).
2. enji-auth calls Collector API: `GET /employees/get_id_by_email?email=user@example.com`
3. Collector returns `{"employee_id": 321}` (or 404 if not found).
4. If 404, enji-auth can call `POST /employees/ensure_by_email` to provision.
5. `employee_id` is included in the encrypted JWT payload.

**File**: `be/services/enji-auth/app/auth/authentication/helpers/collector_client.py`

### This Library's Role

- This library **receives** the encrypted `employee_id` claim in the token.
- It **decrypts and returns** `employee_id` in the `JWTClaims` object.
- It **does not** call Collector — only verifies/transports the claim.

## Verifier: enjilib-jwt-auth Library

**Role**: Decrypts and verifies tokens issued by enji-auth.

### Location

- **Decrypt**: `src/enjilib_jwt/cipher.py`
  - `decrypt_payload(token: str, secret: str) → dict` — decrypts and decompresses `enc` blob
  - Mirrors issuer's `encrypt_payload` in reverse
  
- **Verify & extract**: `src/enjilib_jwt/authenticator.py`
  - `verify_and_extract(token: str) → JWTClaims | None` — full verification pipeline
  - Returns `None` if `enc` is missing or decryption fails (no fallback to flat claims)

### Verification Pipeline

1. **Decode JWT public claims**: `jwt.decode(token, secret, algorithms=["HS256"])`
   - Validates signature with shared secret.
   - Extracts `exp`, `type`, `enc`.
   - **If `enc` is missing**: return `None` (token rejected).

2. **Decrypt `enc` blob**:
   - Base64url-decode the `enc` string.
   - Extract nonce (first 12 bytes).
   - Decrypt ciphertext using AESGCM with derived key.
   - **If decryption fails**: return `None` (e.g., wrong secret, corrupted blob).

3. **Decompress zlib**:
   - Decompress the plaintext JSON.
   - **If decompression fails**: return `None`.

4. **Merge & return**:
   - Parse decompressed JSON.
   - Merge public (`exp`, `type`) + sensitive (all else).
   - Remove `enc` from the final object.
   - Return `JWTClaims` dataclass.

## Compatibility Checklist: Before Changing Shared Token Behavior

**Both issuer (enji-auth) and verifier (this library) must agree on changes.**

### If You Want to Change the Crypto Contract

#### 1. HKDF Info String
- [ ] Current: `b"enji-jwt-payload-encryption"`
- **Do NOT change** unless prepared for all tokens to become undecryptable.
- If must change: version the info string (e.g., `b"enji-jwt-payload-encryption-v2"`), dual-issue tokens during migration window, then deprecate old version.

#### 2. AES Cipher or Key Length
- [ ] Current: AES-256-GCM (32-byte key)
- **Do NOT change** without migration plan.
- If must change: introduce key versioning in the JWT (e.g., `"enc_version": 1` claim), allow verifier to support both algorithms.

#### 3. HKDF Hash Algorithm
- [ ] Current: SHA256
- **Do NOT change** — requires dual-support + migration.

#### 4. Nonce Size
- [ ] Current: 12 bytes (hardcoded `_NONCE_SIZE`)
- **Do NOT change** — breaks all existing tokens.

#### 5. Plaintext Claims Set
- [ ] Current: `{"exp", "type"}`
- **If adding new plaintext claims**: announce breaking change, update both issuer + verifier, version the token format.
- **If moving plaintext to encrypted**: no breaking change, but signals a design shift (why not keep simple?).

#### 6. Zlib Compression
- [ ] Current: `zlib.Z_BEST_COMPRESSION`
- **Do NOT remove** — doubles token size, breaks mobile/legacy clients.
- **If changing level**: low risk; issuer and verifier are independent.

### If You Want to Change Claims Inside `enc`

#### Add New Encrypted Claim
- [ ] Issuer: Update `_create_jwt_token()` to include new claim.
- [ ] Verifier: Update `JWTClaims` dataclass to include new field (backward-compatible if optional).
- [ ] Tests: Add test cases for old tokens (without new claim) and new tokens (with claim).

#### Remove Encrypted Claim
- [ ] **Breaking change** — old tokens will fail `JWTClaims.from_payload()` if the field was mandatory.
- [ ] Plan: Issue deprecation notice, allow dual-reading (old + new format), then remove.

#### Change Encrypted Claim Semantics
- [ ] Example: `roles` was a list, now it's a dict.
- [ ] **Breaking change** — old tokens will fail type validation.
- [ ] Plan: Version the claim, dual-support in verifier, migrate all issuances, then remove old version.

### If You Want to Add New `employee_id` Behavior

- [ ] This library does **not** call Collector.
- [ ] If new lookup or provisioning is needed: change **issuer** (`collector_client.py`), not verifier.
- [ ] Verifier only needs to handle `employee_id` claim if:
  - Type changes (int → string) → version the claim.
  - Semantics change (single int → composite object) → version the claim.

### Pre-Change Verification

1. **Read this contract** and confirm your change.
2. **Update issuer** (`be/services/enji-auth/app/auth/authentication/`).
3. **Update verifier** (this library's `src/enjilib_jwt/`).
4. **Add tests** in both repos (old format, new format, migration scenarios).
5. **Run test suites**:
   - Issuer: `be/services/enji-auth` local tests.
   - Verifier: `cd be/shared/enjilib-jwt-auth && uv run pytest -q`.
   - Integration: Full monorepo test suite.
6. **Create decision record** (new ADR in `docs/decisions/`) explaining why and how.
7. **Link ADR here** in the Related section below.
